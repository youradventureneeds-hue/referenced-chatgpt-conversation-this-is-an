# Candidate accounts and private workspaces

Job seekers register or sign in at `/candidates` and manage their workspace at `/candidate/dashboard`. The header's My account link leads to `/account`, which opens a signed-in user's workspace or offers candidate and employer entry points. A user email belongs to one account type; an existing account is not silently converted between candidate and employer roles.

Candidates can maintain a private name, headline, location, biography, skills, certifications, and HTTPS CV link. Registration and the dashboard’s CV & certifications tab support private document uploads: one PDF CV and up to ten PDF/JPG/PNG certifications, at most 3 MB each and 20 MB per candidate. A new CV replaces the previous file. Metadata and bytes are stored in candidate_documents in the private database. Downloads require the owning candidate session and use attachment/no-store/nosniff headers; no public file URLs are generated. Profiles, files, and CV links are not made public or automatically shared with employers. Nationality is not collected in this flow.

## Saved jobs and application tracking

Every published, approved job detail page has Save this job and Track this application controls. A candidate can bookmark a vacancy and start tracking it as Planning to apply. Applied externally requires an explicit confirmation that the candidate completed the employer's application process. Actual applications continue through the vacancy's application link or the employer's instructions.

The tracker supports private candidate-reported statuses and notes: planning, applied externally, interview, offer received, not selected, and withdrawn. It does not send an application, attach a CV, notify an employer, or receive hiring decisions. Records live separately from the legacy employer-facing Application model so a bookmark or tracker update cannot be mistaken for a delivered application.

Saved jobs and tracked applications preserve the original public title, organization, and country. A removed or unpublished vacancy loses its active link without exposing later private draft changes. If a job is deleted, its optional foreign key becomes null and the candidate retains their own snapshot. Removing a bookmark does not remove its tracker record. Each list holds up to 500 entries.

## Authentication and privacy

Candidate and employer accounts share the password hashing, opaque database-session, and persistent rate-limit implementation. Candidate signup does not return or require a recovery code; employer recovery codes remain supported. Candidate and employer session cookies are separate, and every protected request checks the account's current database role. Copying one role's cookie to the other cookie name does not grant access. No self-service account type can register as ADMIN. Signup defaults to employer for compatibility with the existing employer form; candidate forms explicitly send CANDIDATE.

Candidate sessions last seven days. Candidate Forgot your password sends a random 32-byte reset token by Gmail. The URL carries the token in a fragment so it is not sent in page request URLs; the reset form clears the fragment and submits it only by POST. Only the token digest is stored. Tokens expire after 30 minutes, are consumed once, and are invalidated along with prior sessions when a password is changed. Concurrent resets use transactional claims and a compare-and-set on the prior password digest. Candidate legacy recovery codes cannot reset a password. Password recovery does not change account role. Recovery and sign-out affect the relevant account; candidate actions do not authorize employer APIs or private admin review. Email verification is not configured. Candidate password-reset email is configured at /admin/email using an owner-entered Gmail app password. The SMTP connection is verified and a test email is sent to the owner before saving; the credential is encrypted with the existing 32-byte server encryption key and a separate authentication context. SMTP errors and credentials are never returned in public API responses. Missing mail configuration returns an explicit temporary-unavailability response, and unknown accounts receive the same response as registered candidates.

All profile changes, bookmarks, and tracker mutations require same-origin authenticated requests. Writes bind the user ID from the session rather than trusting form fields. Candidates cannot read or modify another person's data. After sign-in from a job or discussion, return destinations are restricted to validated local `/jobs/<slug>`, `/forum`, or `/forum/<id>` paths. Employers and administrators receive no candidate-profile browsing feature in this release. Account-removal requests use the published support contact.

## Deployment and tests

Apply `prisma/migrations/20261102100000_candidate_portal/migration.sql` and `prisma/migrations/20261102130000_candidate_email_documents/migration.sql` before deploying the generated client. It adds the saved_jobs and candidate_applications tables, using existing user, job, and candidate profile tables. Existing public listings and employer submissions are retained. The second migration adds private documents, reset tokens, and encrypted email settings. The site owner must connect Gmail at /admin/email before password-reset delivery can work. No new deployment secret is required; email encryption uses the existing server encryption key. Gmail app passwords require 2-Step Verification and may be revoked by Google or the account owner.

Run `pnpm test:candidates` for candidate session, cookie, and return-path checks. The existing `pnpm test:employers:integration` suite now exercises both portals against an isolated test schema, including cross-role access, ownership checks, private profile data, duplicate saves, external-application confirmation, unavailable vacancies, deletion-safe snapshots, recovery, and the employer approval flow. See the employer guide for generating the schema SQL and opting into the isolated database tests. The GitHub portal-check workflow runs these tests against its own disposable PostgreSQL service and builds the website.
